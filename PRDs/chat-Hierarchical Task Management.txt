The management of sub-tasks is a structured process facilitated by the `new_task` tool, primarily intended for breaking down complex workflows into discrete, delegable units. The system supports a hierarchical structure, allowing for tasks to have parents and, implicitly, grand-parents, although the sources do not explicitly confirm support for arbitrary, deep *sub-subtask* chains.

Here is a detailed explanation of how sub-tasks are managed:

### 1. Initiation and Delegation (The `new_task` Tool)

The process begins when the Language Model (LLM) uses the **`new_task` tool** (found in `src/core/prompts/tools/new-task.ts` and `src/core/tools/newTaskTool.ts`) in the parent task's thread.

*   **Tool Parameters:** When using the tool, the LLM must provide the **`mode`** (the specialized mode slug, e.g., "code," "debug," "architect") and the **`message`** (the initial instructions) for the new sub-task. Optionally, an initial list of `todos` can be included.
*   **Delegation:** The `newTaskTool` function handles the creation of the new task instance by calling `task.startSubtask`.

### 2. Parent Task Management (Pausing and Waiting)

When a sub-task is successfully created, the parent task transitions into a waiting state:

*   **Parent Paused:** The parent task's state variable `isPaused` is set to `true`.
*   **Child Tracking:** The parent task records the ID of the new child task in its `childTaskId` property.
*   **Mode Preservation:** The parent task records its current mode in `pausedModeSlug`, ensuring it can return to the correct operational mode upon resumption.
*   **Event Emission:** The parent task emits two events: `TaskPaused` (for the parent) and `TaskSpawned` (for the child).
*   **Blocking:** The parent task calls `waitForSubtask()`, which uses an internal interval loop (`pauseInterval`) to monitor the `isPaused` state. This prevents the parent's LLM agent loop from continuing until the sub-task is complete and `isPaused` is reset to `false`.

### 3. Sub-task Execution

The child task operates independently, guided by its new mode and the instructions delegated in the message parameter.

*   **Root and Parent IDs:** The child task instance is initialized with `rootTaskId` (inherited from the parent) and `parentTaskId` (set to the parent's ID).
*   **Mode Switch:** After creation, the parent temporarily switches the workspace mode to the child's designated mode (e.g., "code") to match the sub-task's environment.

### 4. Completion and Resumption

When the child task successfully completes its work, the flow reverses:

*   **Child Completion:** The child task signals completion by using the **`attempt_completion` tool**, providing a concise yet thorough summary of the outcome in the `result` parameter. The child then calls `providerRef.deref()?.finishSubTask(result)`.
*   **Resumption:** The parent task's `isPaused` flag is set back to `false` (usually within `finishSubTask`, though the source mentions `clearCurrentTask` uses `finishSubTask`).
*   **Context Integration:** Upon resumption (when `waitForSubtask` resolves), the sub-task's final result (`lastMessage`) is added to the parent's conversation history. This ensures the LLM receives the outcome of the delegated work before determining the next step in the parent task. The `skipPrevResponseIdOnce` flag is set to ensure the next API call respects the full context including the sub-task result.
*   **Mode Reversion:** The system checks if the global mode changed during the sub-task's run. If it did, it switches back to the parent's `pausedModeSlug`.

### Does it Allow for Sub-Subtasks?

The system supports a hierarchical chain of tasks:

*   A task instance explicitly stores its `parentTaskId`.
*   Crucially, the task also stores its `rootTaskId`, allowing tracking back to the original, top-level task.
*   The system includes a special `Orchestrator` mode, whose custom instructions explicitly define its role as delegating complex tasks into logical **subtasks** using the `new_task` tool. The use of nested task creation within evaluation runs is also implied by the event system, which includes the `TaskSpawned` event.

While the sources demonstrate Parent -> Child task relationships (tracked via `parentTask`, `rootTask`, and `childTaskId`), **the structure inherently supports nesting deeper** (A -> B -> C), as Task B can delegate a new task (Task C) and become Task C's parent, while maintaining A as the root. The *Orchestrator* prompt encourages breaking down tasks into subtasks, implying this multi-level delegation is a core feature of complex workflows.

The **`TaskCompleted` event** payload explicitly includes a field indicating whether the completed task `isSubtask` (`isSubtask: z.boolean()`) and the API implementation records this based on the presence of a `parentTaskId` (`isSubtask: !!task.parentTaskId`), confirming that the system tracks this lineage.

The system manages sub-tasks using the **`new_task` tool** to create a distinct, nested task instance, thereby facilitating complex, multi-step agentic workflows, especially when using the `orchestrator` mode.

## 2. Hierarchical Sub-tasks (Sub-subtasks)

The architecture supports the creation of tasks that are both children (`parentTaskId`) and potential parents themselves, meaning sub-subtasks are inherently possible.

*   Every task tracks its lineage through optional properties: `rootTaskId` and `parentTaskId`.
*   When a child task (Sub-task) is created, it can, in turn, use the `new_task` tool to create its own child task (Sub-subtask), because the `Task` class implements the necessary methods (`startSubtask`, `waitForSubtask`, `completeSubtask`).
*   The `TaskCompleted` event explicitly includes a property `isSubtask` (`z.boolean()`), which is determined by checking the presence of a `parentTaskId` (`!!task.parentTaskId`).

public async startSubtask(message: string, initialTodos: TodoItem[], mode: string) {
    const provider = this.providerRef.deref()
    if (!provider) {
        throw new Error("Provider not available")
    }

    const newTask = await provider.createTask(message, undefined, this, { initialTodos })

    if (newTask) {
        this.isPaused = true // Pause parent.
        this.childTaskId = newTask.taskId
        await provider.handleModeSwitch(mode) // Set child's mode.

        this.emit(RooCodeEventName.TaskPaused, this.taskId)
        this.emit(RooCodeEventName.TaskSpawned, newTask.taskId)
    }

    return newTask
}

### ASSISTANT
Based on the architectural analysis of RooCode's task management system, here's a research-backed strategy to optimize multi-level sub-task delegation while addressing key limitations in the current implementation:

### Core Findings from System Analysis
1. **Inherent Support for Deep Nesting**: 
   - The `rootTaskId`/`parentTaskId` lineage tracking and recursive `Task` class methods (`startSubtask`/`waitForSubtask`) *technically* support arbitrary nesting depth
   - **Critical Gap**: Mode switching uses global state (`provider.handleModeSwitch`), causing collisions in nested scenarios where multiple subtasks try to control workspace mode simultaneously

2. **Blocking Mechanics Limit Concurrency**:
   - Parent tasks use CPU-intensive polling (`pauseInterval`) while waiting, preventing parallel subtask execution
   - No mechanism exists for siblings (multiple children of same parent) to run concurrently

3. **State Corruption Risks**:
   - Single `childTaskId` reference per task prevents tracking multiple children
   - `pausedModeSlug` restoration assumes no intermediate mode changes by grandchildren

### Optimized Architecture Recommendations

#### 1. **Mode Isolation with Context Stacking** (Critical Fix)
```typescript
// src/core/task/TaskProvider.ts
class TaskProvider {
  private modeStack: {taskId: string, mode: string}[] = [];

  async pushMode(taskId: string, mode: string) {
    this.modeStack.push({taskId, mode});
    await this.setGlobalMode(mode); // Actual workspace switch
  }

  async popMode(expectedTaskId: string) {
    if (this.modeStack[this.modeStack.length-1].taskId !== expectedTaskId) {
      throw new Error("Mode stack corruption detected");
    }
    this.modeStack.pop();
    const newMode = this.modeStack.length > 0 
      ? this.modeStack[this.modeStack.length-1].mode 
      : defaultMode;
    await this.setGlobalMode(newMode);
  }
}
```
**Implementation in Task.ts**:
```typescript
// Replace current mode handling in startSubtask/completeSubtask
public async startSubtask(...) {
  await provider.pushMode(this.taskId, mode); // Push to stack
}

public async completeSubtask(result: string) {
  await provider.popMode(this.taskId); // Pop with verification
}
```

#### 2. **Non-Blocking Hierarchy Management**
- **Replace polling with event-driven resumption**:
```typescript
// Task.ts
private subtaskCompletion = new EventEmitter();

public async waitForSubtask() {
  return new Promise<void>(resolve => {
    this.subtaskCompletion.once('completed', () => {
      this.isPaused = false;
      resolve();
    });
  });
}

// In completeSubtask()
this.subtaskCompletion.emit('completed');
```

- **Support sibling concurrency**:
```typescript
// Task.ts modifications
childrenTaskIds: string[] = []; // Array instead of single childTaskId
isPausedForChildren: boolean = false;

public async startSubtask(..., concurrent: boolean = false) {
  if (!concurrent) {
    this.isPausedForChildren = true;
    this.childrenTaskIds = [newTask.taskId]; // Reset for sequential
  } else {
    this.childrenTaskIds.push(newTask.taskId); // Append for parallel
  }
  // ... rest unchanged

// New method for parallel wait
public async waitForAllChildren() {
  return Promise.all(this.childrenTaskIds.map(id => 
    provider.getTask(id).waitForCompletion()
  ));
}
```

#### 4. **Subtask Orchestration Protocol**
Introduce dedicated orchestration handlers:
```typescript
// src/core/orchestration/TaskOrchestrator.ts
class TaskOrchestrator {
  // Handles complex delegation patterns
  async executeSequentialSubtasks(task: Task, subtaskDefs: SubtaskDefinition[]) {
    for (const def of subtaskDefs) {
      const child = await task.startSubtask(def.message, def.todos, def.mode);
      await task.waitForSubtask(); // Sequential blocking
      // Process child result before next subtask
    }
  }

  async executeParallelSubtasks(task: Task, subtaskDefs: SubtaskDefinition[]) {
    const children = await Promise.all(
      subtaskDefs.map(def => task.startSubtask(def.message, def.todos, def.mode, true))
    );
    await task.waitForAllChildren(); // Non-blocking wait
    return children.map(c => c.result); // Aggregate results
  }
}
```

### Critical Workflow Adjustments
1. **Mode Switching Protocol**:
   - **Never** switch modes directly in `startSubtask`
   - Subtasks declare required mode in metadata, resolved during execution
   - Global mode changes only occur at leaf nodes (no subtasks)

2. **Completion Propagation**:

3. **Error Handling Protocol**:
