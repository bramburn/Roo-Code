### Analogy for Understanding the Shift

The migration from Roocode's manual loop to LangGraph is like shifting from driving a car with a **manual transmission** to driving a car with an **automatic transmission (CVT)**.

- **Manual Loop (Roocode):** You, the developer, are the driver. You manually decide: `if (tool_succeeded) { shift_to_next_step(); } else { stop(); }`. You are responsible for the entire control flow logic, clutch, and gear sequence.
- **Phase 1 (Tool Standardization):** You install a standard interface for all the car's components (engine, wheels, brakes) so the computer (LLM) knows exactly how to request an action (e.g., "request throttle 50%", not "press the pedal 5cm").
- **Phase 2 (LangGraph):** You install the automatic transmission. You simply define the overall goal ("drive forward"), and the **LangGraph engine** handles the complex, invisible machinery of checking state, managing the queue, deciding if the transmission needs to pause for human input (Interrupts), or cycling automatically (Edges) to reach the destination.

This is a highly relevant query for the migration, as moving from an imperative loop (Roocode's existing `Task` management) to a declarative framework (LangGraph/Runnables) shifts how and when asynchronous events—which drive the frontend updates—are generated and delivered.

The key to ensuring all emitted calls reach the frontend is leveraging LangChain/LangGraph's **Callback System** and **Streaming mechanisms** to replicate or enhance Roocode's existing event publication structure.

Here is how you can manage the emitted calls back to the frontend and the awareness points for the migration:

---

### 1. Ensuring All Emitted Calls Reach the Frontend

In LangChain/LangGraph, the mechanism for tracking intermediate steps and outputs—which typically constitutes the "emitted calls" sent to the frontend—is the **Callbacks** interface and **Streaming** methods.

#### A. The Callback System (for Events and Status)

The LangChain ecosystem uses **Callback Handlers** (`BaseCallbackHandler`) to intercept internal events across the execution lifecycle (LLM calls, chain steps, tool runs). You should develop a custom callback handler tailored to translate LangChain events into the Roocode frontend's expected events (like `RooCodeEventName.Message`, `RooCodeEventName.TaskModeSwitched`, etc.).

**Key Callback Methods to Implement:**

1.  **Tool Execution Events:**
    - `handleToolStart()`: Use this to signal the frontend that a tool (like `write_to_file` or an MCP tool) is about to run. This mirrors the start of a procedural action in the old loop.
    - `handleToolEnd()`: Use this to relay the tool's final result or status, mimicking the completion of a tool operation.
2.  **LLM Interaction Events:**
    - `handleLLMStart()`: Signals the start of the LLM reasoning phase.
    - `handleLLMEnd()`: Signals when the LLM has completed generating a message or a tool-call plan.
3.  **Intermediate Text/Progress:**
    - `handleLLMNewToken()`: If LLM responses are streamed, this method is invoked for every token chunk generated. This is crucial for providing real-time text output to the user interface, replacing the need for manual incremental message updates.
    - `handleText()`: Can be used to emit general intermediate text updates during chain execution.

**Data Structure Translation:**
Your custom callback handler receives structured data (like `AIMessage`, `ToolMessage`, `ChatGenerationChunk`) and must transform it into the payload structure expected by the frontend (e.g., matching the payloads seen in Roocode's `TaskSocketEvents.EVENT` which include `type`, `taskId`, and message data).

#### B. Streaming (for Real-time Text Output)

LangChain's **Runnables** (which encapsulate agents and graphs) support streaming via methods like `.stream()` or `.streamEvents()`.

- When you execute the compiled graph (Phase 2), instead of calling `.invoke()`, you should use **`.stream()`** or **`.streamEvents()`**.
- When a Runnable (like a `ChatModel`) is configured for streaming, it emits **`AIMessageChunk`** data iteratively.
- The frontend must consume this iterable stream to receive token chunks immediately, which is essential for perceived responsiveness. The implementation for handling new tokens usually involves passing a callback function into the `callbacks` field of the invocation configuration.

### 2. Key Migration Awareness Points

You must be aware of the shift from explicitly triggering events (`this.emit(RooCodeEventName.Message, ...)`) to passively receiving standard events, and how to manage special Roocode/MCP events:

#### A. Centralised Event Management vs. Decoupled Components

- **Awareness Point:** In LangChain, event handling is **decentralised**. Events are managed by the **`CallbackManager`**. Your primary integration point should be registering your custom handler globally or passing it into the `callbacks` configuration during the `.invoke()` or `.stream()` call.
- **Roocode Context:** You need to ensure your custom callback handler has access to necessary Roocode context (like the `taskId` and mechanisms for sending messages to the Webview/Socket) to correctly format and dispatch the event payloads.

#### B. Handling Non-LLM/Non-Tool Events (Custom Events)

Roocode likely has custom status or lifecycle events (like `RooCodeEventName.TaskModeSwitched` or `TaskInteractive` events).

- **LangGraph Solution:** You can use **Custom Events** within LangChain Runnables to represent these specific lifecycle or status updates. The `streamEvents` method supports surfacing these custom events in the output stream.
    - Within a `RunnableLambda` function (which would execute custom task logic inside a LangGraph node), you can call a utility function (like `dispatchCustomEvent`) to emit a custom event with a user-defined name and data.
    - The frontend consumption layer must check for `event.event === "on_custom_event"` to capture these messages.

#### C. Handling Interactive Interrupts (Human-in-the-Loop)

Roocode's mechanism for waiting for human confirmation (`TaskInteractive` or `presentResumableAsk`) is replaced by LangGraph's **Interrupts** and **Commands**.

- **Awareness Point:** When the graph enters an interrupted state (e.g., waiting for manual approval of a sensitive MCP tool or file write), the execution flow pauses, and the agent must be explicitly resumed with a `Command({ resume: HITLResponse })`.
- The migration must ensure that when an interrupt occurs, a specific signal is emitted to the frontend to trigger the UI (e.g., `handleHumanRelayResponse`), and the frontend response (`response.text`) is correctly wrapped in a `Command` object to restart the graph execution.

#### D. MCP Notifications

If your MCP client supports notifications (like `onLog` or `onToolsListChanged`), you must configure the `MultiServerMCPClient` to listen to these. These notifications are external to the core graph execution flow but must still be relayed to the frontend alongside standard task events.

- The `MultiServerMCPClient` configuration includes a `notifications` block where you can define handlers (e.g., `onLog`) to capture these messages and relay them to the frontend outside of the primary stream.
